# ТЗ: оставшиеся работы по Vane (после cutover :443)

Статус на момент написания: прод `:443` держит `vane` (per-request dispatch, самопродление ACME до Jan 2027), `penik-proxy` остановлен, Caddy жив на `:80`/`:8444` как fallback. Паритет 25 сайтов побайтово подтверждён. Настоящий документ — единственный источник списка недоделок; всё закрытое ранее здесь не дублируется, только точкой отсчёта.

## P0. Стабильность ACME (блокирует продления)

### TZ-1. Singleflight вокруг `ensure_certificates`
**Проблема (факт из журнала 13.10, две волны 11:35:20–22 и 11:35:24–31):** inotify-авторелоад, ручной SIGHUP и 12-часовой таймер запускают `ensure_certificates` параллельно. Каждый заказ висит 80+ секунд (60с sleep propagation). LE переиспользует pending-авторизации между параллельными заказами → одинаковый digest → второй `create_txt_record` падает с `81057 An identical record already exists`, валятся все заказы пачкой.
**Требование:** взаимное исключение (singleflight/mutex) на весь `ensure_certificates`: повторный триггер во время выполняющегося либо ждёт завершения, либо пропускается с `info`-логом. Покрыть тестом с двумя конкурентными вызовами.
**Приёмка:** два релоада подряд с интервалом <90с → в журнале один заказ, ноль `identical record`.

### TZ-2. Coverage pre-check в `order_partitioned`
**Проблема:** фолбэк заказывает **все** apex-группы безусловно, без проверки покрытия. Любой вечно-падающий домен (см. wlun ниже) превращает каждый ensure (12ч + каждый reload) в успешный перевыпуск penik+slavchat. Лимит дубликатов LE — 5/неделю на набор SAN: исчерпывается за ~2 дня, после чего блокируются и настоящие продления (скользящая неделя).
**Требование:** перед заказом каждой партиции проверять покрытие её доменов через `has_certificate_for` (порог 30д); покрытые группы пропускать с `info`-логом.
**Приёмка:** при свежем unified-серте любой ensure заканчивается `skipping` без единого заказа в журнале и без новых файлов в store.

### TZ-3. Чистка протухших `_acme-challenge` TXT при старте
**Проблема (факт):** рестарт поверх выполняющегося заказа убивает процесс до cleanup-фазы — TXT-записи утекают (найдено и удалено вручную 4 штуки 13.10). Мусор в DNS-ответах + путаница при отладке.
**Требование:** при старте, до первого ensure, удалять все `_acme-challenge.*` TXT в управляемых зонах (зоны — из успешного `get_zone_id` по apex'ам сайтов). Только свои `_acme-challenge`-имена, ничего чужого не трогать. Ошибки API — `warn`, не фатально.
**Приёмка:** после `restart` во время заказа в зонах ноль висячих TXT.

## P1. Чужие зоны: кейс wlun.eu.cc

Контекст: `eu.cc` — чужой реестр, зоны нет в Cloudflare-аккаунте (`zone not found`, подтверждено), certbot lineage никогда не было. Файл сайта сейчас в `/etc/vane/sites-available/` **без** симлинка в `sites-enabled/` (припаркован: включённым он ломает unified-заказ и включает спираль из TZ-2).

### TZ-4. ALPN-01-фолбэк при отсутствии зоны
**Требование:** если `get_zone_id(apex)` не нашёл зону, заказывать exact-домены этой apex-группы через TLS-ALPN-01 (vane слушает `:443`, реестр челленджей и резолвер уже умеют ALPN) вместо провала всего заказа. Wildcard-домены без зоны — пропускать с понятным `warn` (ALPN их не умеет по RFC).
**Приёмка:** `wlun.eu.cc` получает валидный LE-сертификат без зоны в CF; `openssl verify` зелёный; браузер без варнингов.
**Временный обход (без кода, задокументировать в README):** именованные `wlun.eu.cc.fullchain.pem` + `wlun.eu.cc.privkey.pem` в `storage_dir` (добыть хоть `certbot --manual`) — vane отдаёт сразу, ACME не трогает.

## P1. Паритет статики с Caddy

### TZ-5. Etag + Last-Modified + 304
**Проблема:** статика vane не ставит `Etag`/`Last-Modified` (проверено grep: упоминаний нет) → нет условного кэширования, каждый ревалид тянет тело целиком.
**Требование:** в `serve_static_file` (`static_files.rs:30`, единая точка для `file_server`/`try_files`/фолбэков): `Etag: "<mtime_unix_hex>-<size_hex>"` (формат как у Caddy — нагретые им кэши продолжат валидироваться), `Last-Modified` в IMF-fixdate, только GET/HEAD. Порядок RFC 9110 §13.2.2: `If-None-Match` (`*` или совпадение) → 304, иначе `If-Modified-Since` (секундная гранулярность) → 304. Ответ 304: без тела, с `Etag` (+`Last-Modified`, `Cache-Control`), без `Content-Length` тела и без `Content-Encoding`. Для этого в `serve_static_file` пробросить заголовки запроса (сейчас их нет в сигнатуре — обновить 4 вызова в `service.rs`).
**Приёмка:** повторный запрос с `If-None-Match` → 304; неверный etag → 200.

### TZ-6. Accept-Ranges + 206
**Проблема:** нет `Accept-Ranges`, нет `206` → недокачка и перемотка сломаны (критично для `music/*.mp3` и аттачментов).
**Требование:** `Accept-Ranges: bytes` на файловых 200/206; парсинг `bytes=A-B | A- | -N` (один диапазон) → `206` + `Content-Range` + точный срез; мимо размера → `416` + `Content-Range: bytes */size`; мультидиапазоны — обычный 200 целиком (задокументировать); `If-Range` mismatch → 200 целиком; валидный Range отключает gzip для ответа (identity-срез, без `Content-Encoding`). Прокси не трогать (Range/206 там уже пробрасываются прозрачно).
**Приёмка:** `curl -r 0-99 <mp3>` → 206:100 = head файла; перемотка аудио в браузере.

Похороны Caddy** (после 7–30 дней soak + одно естественное самопродление ~середина декабря): снять `default_backend` (или оставить Caddy вечным sink'ом для мусора/ECH — стоит ноль), остановить `:80`/`:8444`/`:2019`, **удалить iptables-правило UDP 443→8444**, погасить `certbot.timer`, через 30 дней удалить юнит и бинарь `penik-proxy`. ## Зафиксированные решения (не пересматривать без причины)

- Дефолт `request_body` 250 МБ — оставлен по требованию (413 проверен живым аплоадом 300 МБ за ~1с).
- `staging=false` (продовый LE сразу), порог продления 30д, проверки каждые 12ч + на reload, propagation 60с.
- ACME-аккаунт `admin@slavchat.ru`, unified multi-SAN + per-apex именованные копии; резолвер отдаёт свежий unified (создан позже именованных).
- Откат на каждом этапе: `systemctl stop vane && systemctl start penik-proxy` (+ `start caddy` при необходимости). Бинарь и юнит `penik-proxy` не удалять до Фазы 3.
